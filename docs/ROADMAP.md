# 揪Formosa 產品路線圖

規劃師交付物。定義**做什麼、為什麼、以什麼順序**，以及每一項的完成標準。

實作規格在 `docs/tasks/T-xxx.spec.md`。開發師接手時把 `status: planned`

## 缺什麼——三個層次的判斷

**一、使用者現在做不到但會想做的事**
搜尋、知道社團在哪裡、標記「我要參加」、被提醒。

**二、團長現在做不到但需要做的事**
上傳社團照片、編輯已送出的資料、看到自己的曝光成效。

**三、平台現在缺的東西**
審核介面（送出的社團沒人審就是死路）、檢舉機制、SEO。

## 刻意不做的事

規劃的一半是決定不做什麼。以下每一項都被考慮過並否決：

| 不做 | 理由 |
|---|---|
| 站內聊天 / 私訊 | 社團已經有 LINE 群，重造一個沒人會用，且帶來內容審查責任 |
| 報名收費 / 金流 | 法遵成本極高（第三方支付、退款、發票），而原站也刻意不碰 |
| 使用者評價社團 | 公開評分真實社團會產生名譽風險，且容易被刷 |
| 訓練紀錄 / 里程統計 | Strava 已經做得很好，重疊沒有價值 |
| 原生推播（FCM/APNs） | 本地通知已能解決「忘記」問題，推播需要伺服器與憑證維運 |

## 排序的依據

不是照「哪個好做」，而是照**這條使用者路徑上最先斷掉的地方**：

```
發現社團 → 判斷合不合適 → 決定參加 → 記得出席 → 回訪
   ↑            ↑              ↑          ↑
Phase 1     Phase 1        Phase 2    Phase 2
（搜尋/地圖） （照片/距離）    （RSVP）   （提醒）
```

平台側（Phase 3）排在後面，是因為在開放真實使用者之前它不會被觸發。
但它是**開放的前提**，不是可選項。

## 給開發師的交接方式

1. 從 `dev` 切分支：`git checkout -b feat/T-070-search`
2. 把 `docs/tasks/T-070.spec.md` 的 `status` 改為 `spec_frozen`
3. 依 spec 實作，每個 `Scenario:` 都要有 `// @spec T-070/Scenario-Xxx` 的測試
4. `bash tool/harness.sh` 全綠
5. PR 到 `dev`

規格凍結後**不要改規格去配合實作**。實作不了就回報 `spec_defect`，
由規劃師修規格——這個方向不能反過來，否則規格會被實作慢慢侵蝕成事後描述。
